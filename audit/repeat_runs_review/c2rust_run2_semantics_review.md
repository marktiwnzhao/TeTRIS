## 六个浮点样本

文件名时间分别为 08-25-31、08-30-05、08-30-45、08-32-04、08-33-25、08-36-37。每个样本的原始 C 第 15 行将 `ft_ptr` 初始化为 `&why`，之后没有改变指针。第 25 行实际执行了嵌套复合赋值；右侧既读取 `*ft_ptr`，又在未排序的另一子表达式中修改它。

代表性结构（省略其他计算）：

```c
float *ft_ptr = &why;
local_float = *ft_ptr += *ft_ptr + /* ... */ (*ft_ptr += *ft_ptr);
```

只在内存中将确定的 `*ft_ptr` 别名展开成 `why`，移除不再需要的指针声明，交给 Clang 17 `-x c - -fsyntax-only -Wunsequenced`。六个样本全部报告 `unsequenced modification and access to 'why'`。结合执行路径和确定别名，符合 [C11 §6.5p2](https://www.sigbus.info/n1570#6.5p2) 的未定义行为条件；不是普通浮点舍入误差。未改变原始文件。

## 整数/状态样本

样本：`id:000131,src:000089,time:12-15-21`，源 C 第 61 行 `case 0`。`global_int += ... reply(...) ...` 同时涉及复合赋值左侧值和会更新该全局变量的函数调用。

在已有 C 控制程序上使用 GDB 跟踪：第五次 `reply()` 前 `global_int=-264`，返回后 `global_int=-334`。反汇编显示，复合赋值最终相加时读取的是调用后的值；生成 Rust 第 344–361 行在调用前读取左侧值。

| 执行/对照 | 输出 |
|---|---|
| 原 C 控制程序 | `-857849:-82126.68:-71` |
| 已保存的 Rust 输出 | `-857779:-82126.68:-71` |
| GDB 中第五次调用返回后，将该次最终读取的值恢复为调用前的 -264，再继续 C | `-857779:-82126.68:-71` |

差值恰为 70。GDB 对照仅修改该次运行的进程内存，不修改源代码或可执行文件。依据 [C11 §6.5.2.2p10](https://www.sigbus.info/n1570#6.5.2.2p10)，调用者的求值与函数体执行在此处可以有不同的先后顺序；不能因为函数修改全局变量就一概判为未排序 UB，也不能要求 Rust 复制特定 C 编译器选择的顺序。该证据解释了当前观察差异，并非对整个程序所有潜在问题的形式化证明。
